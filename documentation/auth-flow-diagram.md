# Auth Flow Diagram

After every workflow execution, Auth Playground generates an interactive **sequence diagram** that visualizes the entire authentication and tool-call sequence. This makes it easy to understand what happened during a run — which tokens were exchanged, which tools were called, and in what order.

---

## Accessing the Diagram

Click **"View Auth Flow"** in the chat panel toolbar after a workflow run. The diagram opens in the right panel.

---

## What the Diagram Shows

The diagram adapts based on the type of workflow:

### No Auth (`flow: 'none'`)

```
User → App → Agent → (tool calls, if any) → Agent → App → User
```

Shows the basic request/response cycle and any MCP tool calls made by the agent.

### Agent OAuth2 Flow (`flow: 'agent'`)

```
User → App → Agent
Agent → IAM: POST /oauth2/authorize
IAM → Agent: { flowId, authenticatorId }
Agent → IAM: POST /oauth2/authn (credentials)
IAM → Agent: { authCode }
Agent → IAM: POST /oauth2/token
IAM → Agent: { access_token }
Agent ↔ LLM: tool decision steps
Agent → MCP: tool calls (Bearer token)
MCP → Agent: results
Agent → App → User: final answer
```

### OBO Flow (`flow: 'obo'`)

```
User → App: message
App → Agent: forward
Agent → IAM: agent authentication (3-step)
IAM → Agent: access_token
Agent → App: build /oauth2/authorize URL
App → User: show Authorize button
User → IAM: GET authorize URL (login + consent)
IAM → User: redirect with code
User → Agent: code via BroadcastChannel
Agent → IAM: POST /oauth2/token (actor_token = agentToken)
IAM → Agent: OBO token
Agent ↔ LLM: tool decisions
Agent → MCP: tool calls (OBO token)
MCP → Agent: results
Agent → App → User: final answer
```

---

## Diagram Lanes

| Lane | Represents |
|------|-----------|
| **User** | The human sending the chat message |
| **App** | The Auth Playground frontend |
| **Agent** | The AI Agent (server-side executor) |
| **IAM** | The Asgardeo identity provider (shown only when OAuth2 is used) |
| **LLM** | The AI model (e.g., `openai / gpt-4o`) |
| **MCP Server(s)** | One lane per connected MCP Client node |

---

## Interactive Controls

### Step Slider

Drag the slider to advance through the sequence step by step. Messages appear with a fade-in animation as you progress.

### Animate Button

Starts automatic playback from the current step. The animation advances through all messages in order. Loops at the end.

### Show All Button

Jumps to the final step and disables autoplay. Useful for seeing the complete diagram at once.

---

## Color Coding

| Color | Meaning |
|-------|---------|
| Default gray | Standard request/response messages |
| Amber (`#d97706`) | OAuth2 authentication steps |
| Blue (`#2563eb`) | Tool calls from agent to MCP server |
| Green (`#059669`) | Successful tool results |

---

## Token Inspection

For each OAuth2 flow, the diagram displays:

- A truncated preview of the token (e.g., `eyJhbGc...3RlN`)
- A **[decode on jwt.io]** link that opens the token in the JWT debugger for inspection

The full token is never displayed. The preview is generated by `previewToken()`, which shows the first and last few characters only.

## Trace Data Structure

Every execution produces a `WorkflowTrace` object, attached to the final SSE `result` event:

```typescript
interface WorkflowTrace {
  flow: 'agent' | 'obo' | 'none'
  startedAt: number        // Date.now() at start
  finishedAt?: number      // Date.now() at end
  userMessage?: string
  finalAnswer?: string
  llm?: { provider: string; model: string }
  mcps: MCPNodeTrace[]
  tools: ToolCallTrace[]
}
```

### MCPNodeTrace

Records the auth details for each MCP Client node:

```typescript
interface MCPNodeTrace {
  nodeId: string
  name?: string           // friendly name from node config
  endpoint: string        // MCP server URL
  flow: 'agent' | 'obo' | 'none'
  iamBaseUrl?: string
  authorizeUrl?: string
  authnUrl?: string
  tokenUrl?: string
  oboAuthUrl?: string     // auth URL shown to the user
  agentToken?: string     // access token from agent flow
  oboToken?: string       // access token from OBO flow
  agentId?: string
}
```

### ToolCallTrace

Records every tool call made during the agent loop:

```typescript
interface ToolCallTrace {
  step: number            // 1-indexed loop iteration
  publicName: string      // normalized tool name the agent used
  sourceToolName: string  // original MCP tool name
  endpoint: string        // MCP server URL
  nodeId: string
  args: string            // JSON.stringify of arguments
  result: string          // truncated to 500 chars
  ok: boolean             // true if call succeeded
}
```

---

## Flow Classification

The diagram determines the flow type from the MCP nodes:

```
dominantFlow(mcps):
  if any mcp.flow === 'obo'   → 'obo'
  if any mcp.flow === 'agent' → 'agent'
  else                        → 'none'
```

The OBO flow takes precedence if any node uses it.

---

## Collapsible Sections

The diagram panel includes two collapsible sections at the bottom:

### MCP Servers

Lists each connected MCP Client node with:
- Server name (or node ID)
- Endpoint URL
- Flow type (agent / obo / none)
- Token preview + jwt.io link

### Tool Calls

Lists every tool call the agent made:
- Step number
- Public tool name (normalized)
- Original tool name
- Arguments (collapsed JSON)
- Result (truncated)
- Success / failure indicator

---

## Tips

- Use the diagram to **debug unexpected behavior** — you can see exactly which tool was called with which arguments and what it returned.
- The **jwt.io link** lets you inspect token claims (subject, expiry, scopes) without decoding manually.
- If a tool call shows `ok: false`, expand the result to see the error message from the MCP server.
- For OBO flows, the diagram shows both the `agentToken` (from agent auth) and the `oboToken` (user-delegated) so you can verify both were obtained.
